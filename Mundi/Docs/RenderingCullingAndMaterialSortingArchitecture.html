GPU HZB 실제 Scene Depth 기반

현재 프레임 Depth를 계층화하고 World AABB를 투영해, 가려진 메시의 다음 제출을 생략한다.

45,002 → 2 관측된 Material bind 예시

Draw 수는 유지하면서 같은 상태를 연속 배치해 중복 바인딩 비용을 제거한다.

중요 제약: 이 최적화는 메시 여러 개를 하나의 인스턴스 Draw로 합치지 않는다. 살아남은 각 StaticMesh는 여전히 개별 DrawIndexed로 제출된다. 따라서 Culling은 Draw Call 수를 줄이고, Sorting은 Draw Call 사이의 상태 변경을 줄인다.

현재 프레임의 렌더링 흐름

세 최적화는 서로 대체 관계가 아니라 서로 다른 단계의 낭비를 제거한다.

1. CPU Frustum Culling

원리

카메라의 View-Projection 행렬에서 6개 평면을 만들고, 각 BVH 노드의 AABB가 평면의 완전히 바깥인지 검사한다. 바깥이면 그 노드 아래의 모든 컴포넌트를 한 번에 건너뛴다.

좌 / 우 / 상 / 하 / Near / Far

현재 구현의 특징

  • 기존 4면뿐 아니라 Near/Far까지 포함한 완전한 6면 검사
  • 개별 메시 전수 검사 대신 BVH subtree 단위 early-out
  • 노드가 Frustum 안에 완전히 포함되면 자식 재검사 없이 연속 범위를 결과에 추가
  • MeshComponent뿐 아니라 공간 정보를 가진 SceneComponent 등록 경로를 일원화
  • 레벨 대량 등록 시 bulk 갱신으로 BVH 재구축 횟수 억제
1
공간 등록SceneComponent의 등록·해제와 위치 변경이 WorldPartition의 spatial revision을 갱신한다.
2
BVH 질의노드 AABB가 Frustum 밖이면 subtree 전체를 제거한다.
3
후보 전달살아남은 컴포넌트만 Scene proxy 및 MeshBatch 생성 후보가 된다.
효과가 큰 상황: 카메라 뒤 또는 시야 좌우에 오브젝트가 많거나, BVH가 공간적으로 잘 분리된 넓은 맵. 모든 메시가 화면 안에 들어오는 전경 샷에서는 자연스럽게 제거량이 작다.

2. GPU HZB Occlusion Culling

Frustum 안에 있지만 다른 물체의 실제 픽셀에 완전히 가려진 메시를 찾는다. CPU가 추정 Depth를 만드는 방식이 아니라 GPU의 SceneDepth를 입력으로 사용한다.

HZB 생성

Depth Buffer를 작은 mip들로 반복 축소한다. 현재 normal-Z 체계에서는 각 2×2 영역의 가장 먼 값(MAX)을 저장해, 영역 전체를 가리는지 보수적으로 판단한다.

SceneDepth → HZB mip 0 → mip 1 → … → 1×1

오브젝트 검사

StaticMesh의 축소하지 않은 실제 World AABB 8개 꼭짓점을 화면으로 투영한다. 투영된 사각형 크기에 맞는 mip을 선택하고, 오브젝트의 가장 가까운 View depth와 HZB depth를 비교한다.

Frame N

현재 준비된 결과를 적용한 뒤 보이는 메시를 그려 SceneDepth를 만든다.

GPU dispatch

Frame N의 Depth로 HZB를 만들고 Frustum 후보 AABB를 compute shader에서 검사한다.

Frame N+1 이후

비동기 readback이 준비되면 결과를 적용한다. 아직 준비되지 않았으면 CPU를 기다리지 않는다.

카메라 이동 중 안정성을 위한 장치

장치구현 의도

3. Material Sorting과 정적 Draw Cache

Material Sorting은 Draw Call 자체를 합치지 않는다. 같은 GPU 상태를 사용하는 MeshBatch를 붙여 놓고, 직전 상태와 같으면 중복 API 호출과 resource bind를 생략한다.

정렬 키

  1. Shader
  2. Material
  3. Vertex Buffer
  4. Index Buffer
  5. Stride
  6. Primitive Topology

상위 키가 같을수록 하위 상태도 연속될 가능성이 높아진다.

Draw 시 상태 캐시

현재 바인딩된 Material, Shader, VB, IB 등의 포인터/값을 기억한다. 다음 MeshBatch가 동일한 상태면 해당 bind를 건너뛰고 상수 데이터와 개별 DrawIndexed를 계속 제출한다.

영구 StaticMesh Draw Cache

매 프레임 동일한 StaticMesh의 batch metadata를 다시 구성하고 전체 정렬하는 CPU 비용을 줄인다. World 공간 revision, ResourceManager shader revision, StaticMesh draw-cache revision을 key로 삼아 변경 시에만 다시 만든다.

캐시 무효화

  • 컴포넌트 추가·제거 및 레벨 교체
  • StaticMesh 또는 Material 교체
  • Shader resource 갱신
  • 공간 등록 구조 변경
관측 결과 해석: Culling을 모두 끈 테스트에서 Material bind가 약 45,002 → 2, frame time이 약 4 ms 줄었다면 정상적이고 의미 있는 결과다. Draw Call 45,000개는 그대로이므로, 남은 CPU 제출 비용과 vertex/raster 비용 때문에 FPS가 bind 감소율만큼 오르지는 않는다.

세 최적화의 상호작용

기능주로 줄이는 것잘 보이는 테스트한계
Frustum Culling화면 밖 후보 탐색·Batch·Draw카메라 방향 밖에 메시가 많은 넓은 장면5만 개가 전부 화면 안이면 제거할 수 없음
GPU HZB Occlusion가려진 메시의 Draw와 GPU geometry 비용큰 사과·벽·건물 뒤에 오브젝트가 겹친 장면전부 노출된 장면은 compute/readback 비용만 남을 수 있음
Material SortingShader·Material·Buffer 상태 변경Culling을 끄고 동일 material 메시를 대량 제출Draw Call 및 per-object 상수 갱신은 유지
StaticMesh CacheBatch 재생성·반복 정렬 CPU 비용정적 메시가 많고 scene revision이 안정적인 장면DrawIndexed 실행 비용은 줄이지 않음

Occlusion이 이미 대부분의 메시를 제거하면 Sorting이 처리할 batch 자체가 적어져 Sorting ON/OFF 차이가 작아지는 것이 정상이다. 반대로 전체 노출 장면에서는 Culling의 이득이 줄고 Sorting의 상태 변경 절감이 더 잘 드러난다.
